# Digital Asset QA Automation Overall Guide

This document explains how to continue QA ownership of the Digital Asset Playwright QA repo.

## Repository Purpose

This repo is an independent Playwright QA automation project for the Digital Asset team. It is intentionally separate from product source repos such as Ops-UI and Orchestrator.

Primary goals:

- consume requirement-derived QA test cases generated from the digital-asset-context docs workflow;
- turn those source test cases into UI/API-aware test specifications;
- generate maintainable OpsUI browser tests with Playwright Page Objects;
- migrate Digital Asset Orchestrator Postman/API scenarios into Playwright request-based tests;
- run live smoke/functional/workflow coverage against deployed Digital Asset environments;
- publish automation coverage to Confluence.

## End-To-End QA Workflow

Recommended ownership flow:

1. In the digital-asset-context repo, use its AI skill to read product/architecture docs and generate a source QA test case document.
2. Attach or copy that source QA test case document into the next skill run.
3. In the relevant product repo, run Skill 1 to convert source QA test cases into an implementation-aware test spec. Today Skill 1 is focused on Ops-UI UI awareness.
4. Optionally run Playwright Codegen against the live UI for complex workflows and keep the generated locator sequence as extra input.
5. In this QA repo, run Skill 2 with the QA repo, the attached/provided implementation-aware test spec, and optional Codegen output.
6. Review generated Page Objects, specs, skipped placeholders, and matrices.
7. Run TypeScript checks and the smallest relevant Playwright suite.
8. Generate the Confluence report and publish it when ready.

For Orchestrator backend-only coverage, use the same TC accountability process but implement tests under `tests/api/` with clients under `api/`. Postman collections should be treated as migration references, not as the long-term runner.

## Skill-Based Workflow

### Upstream: Generate Source QA Test Cases

Before Skill 1, the source QA test case document is expected to come from the digital-asset-context repo.

That upstream skill reads documents such as product context, architecture notes, API docs, user stories, and acceptance criteria, then produces an initial QA test case list. At this stage, the test cases may describe business coverage well, but they are not expected to know exact OpsUI component structure, selectors, page labels, Orchestrator API response details, or Playwright implementation details.

### Step 1: Refine Source Test Cases In Product Repo

Use Skill 1:

```text
abd-ops-ui-testcase-refiner
```

Input:

- attached/provided source QA test cases generated from digital-asset-context;
- Ops-UI source code.

Output:

```text
an implementation-aware test spec, using the requested output path when provided
```

Skill 1 is the **product testcase refiner**. The current version is the Ops-UI testcase refiner. It runs in the Ops-UI source repo, where it can read UI routes, components, labels, form controls, state, and selector opportunities.

Skill 1 should inspect the product repo and create an implementation-aware spec. For OpsUI, that means UI routes/components/labels/selectors. It should not generate Playwright scripts directly. Its job is to make the source test cases precise enough for automation.

For transaction workflows, it should classify operations:

- `mint`
- `transfer`
- `burn`
- `mint-transfer`
- `transfer-burn`
- `mint-transfer-burn`

It should also model blockchain network as scenario data. Known networks include:

- `BESU`
- `SEPOLIA`
- `SOLANA`

### Step 2: Generate Playwright Scripts In QA Repo

Use Skill 2:

```text
abd-qa-playwright-generator
```

Input:

- current QA Playwright repo;
- attached/provided implementation-aware test spec;
- optional Playwright Codegen output for difficult workflows.

Output:

- Page Object updates;
- API client updates for `TC-API` cases;
- executable specs;
- skipped placeholders for blocked cases;
- `docs/test-coverage-matrix.md`;
- transaction scenario data and `docs/transaction-scenario-matrix.md`.

Skill 2 is the **QA Playwright generator**. It runs in this QA repo, where it can read the existing Playwright architecture, OpsUI Page Objects, fixtures, Orchestrator API clients, scenario data, specs, and reporting scripts.

Skill 2 should not silently skip TC IDs. Every TC ID must be classified as implemented, implemented-skipped, covered-by-existing, needs-clarification, or blocked.

Skill 2 must respect the QA repo boundary. It cannot assume access to product source repos such as Ops-UI or Orchestrator. If the provided implementation-aware spec conflicts with existing Page Objects/API clients, lacks stable locators, or omits required live account/API data, Skill 2 should ask questions before implementation instead of guessing.

For API test generation, Skill 2 should inspect existing `api/`, `data/api-scenarios/`, and `tests/api/` files first. It should add typed client methods and scenario data rather than embedding large JSON bodies directly in specs.

### API Collection Migration Skill

For API collection migration, use:

```text
abd-postman-api-playwright-generator
```

This skill should be used when a latest Postman collection or API export is attached/provided and the user wants Playwright API tests updated. It should convert selected requests into this repo's API client/scenario/spec pattern, update docs and coverage matrices, and preserve existing tests.

This is useful because Orchestrator APIs may keep evolving. A dedicated skill reduces drift by consistently mapping collection variables, request bodies, auth flow, polling rules, and Postman assertions into the repo's Playwright API architecture.

## Recommended Codegen Process

Before asking Skill 2 to generate a complex workflow, manually record the workflow once:

```bash
npx playwright codegen https://daui.34.36.111.7.nip.io/login
```

Then:

1. log in;
2. perform the workflow, for example mint;
3. copy the generated locator sequence;
4. provide it together with the implementation-aware test spec to Skill 2.

This usually produces better scripts because live UI labels and dropdown behavior may differ from source code.

Do not paste raw Codegen output directly into final specs. Use it as locator evidence, then convert it into Page Object methods and business-readable specs.

## Running Tests

Initial setup:

```bash
npm install
npx playwright install chromium
cp .env.example .env
npm run auth:admin
```

Non-mutating suites:

```bash
npm run test:smoke
npm run test:api
npm run test:functional
npm run test:workflow
```

Single backend API flow:

```bash
npm run test:api:mint
```

The current API MINT flow registers the user if needed, logs in, submits MINT, then polls `GET /v1/transaction/{txId}` until terminal success, currently `status === COMPLETED`.

API tests are split into:

- `tests/api/smoke`: environment/auth reachability checks.
- `tests/api/functional`: endpoint-level validation and negative cases.
- `tests/api/workflows`: multi-step API E2E flows that may create backend transaction data.

Useful commands:

```bash
npm run test:api:smoke
npm run test:api:functional
npm run test:api:workflow
```

API workflow tests are guarded by `OPSUI_RUN_API_MUTATION_TESTS=true`. The focused `npm run test:api:mint` command sets that variable automatically.

Live mutation workflows:

```bash
npm run test:mint
npm run test:transfer
npm run test:burn
npm run test:mint-transfer-burn
npm run test:lifecycle
```

Visible browser / slow mode:

```bash
OPSUI_HEADLESS=false OPSUI_SLOW_MO_MS=500 npm run test:transfer
```

Useful inspection commands:

```bash
npm run inspect:login
npm run inspect:page -- /transactions/new
npm run inspect:page -- /transactions/history
npm run inspect:storage
npm run inspect:history
```

## Local vs Deployed QA Execution

In most teams, QA automation like this repo primarily targets deployed QA/staging/integration Digital Asset environments rather than each QA engineer running the full product locally.

Typical flow:

1. Engineers run unit/component/service tests locally and in CI before merging.
2. The app is deployed to a shared QA/staging/integration environment.
3. QA runs Playwright UI/API smoke and regression tests against that deployed environment.
4. Mutating workflow tests run only against environments with acceptable test data and reset/cleanup policies.
5. CI may run a small smoke subset on every deployment and broader suites on schedule or release candidate builds.

Local Playwright runs are still useful for developing/debugging tests, validating selectors, and reproducing failures. But requiring QA to fully stand up the frontend, backend, auth, database, and third-party simulators locally is usually inefficient unless the product has a strong one-command local environment.

## Adding Transaction Coverage

Do not hardcode source/destination account pairs inside specs.

Add confirmed combinations to:

```text
data/scenarios/transaction-scenarios.ts
```

Each scenario should include:

- flow;
- network;
- source account and vault/id;
- destination account and vault/id;
- expected queue labels;
- expected history labels;
- amount;
- TC IDs.

Update:

```text
docs/transaction-scenario-matrix.md
```

Use smoke scenarios for safe daily checks and reserve broad matrices for explicit regression/full-matrix runs.

When adding a new network such as `BESU` or `SOLANA`, add it as scenario data. Do not fork the spec file just because the network changes.

## Adding API Coverage

Use [API_TEST_README.md](./API_TEST_README.md) as the detailed API guide.

Recommended pattern:

1. Add the request payload to `data/api-scenarios/`.
2. Add reusable methods to `api/AuthApiClient.ts`, `api/TransactionApiClient.ts`, or a new API client.
3. Add the spec under `tests/api/`.
4. Include a `TC-API-...` ID in the test title.
5. Poll backend status for async orchestration flows; do not pass immediately after submit unless the requirement only covers request acceptance.
6. Update `docs/test-coverage-matrix.md` and scenario matrix docs.

For transaction orchestration APIs, validate backend fields such as `transactionId`, `flowType`, `status`, `initiatedByUserId`, `assetId`, `amount`, and `txOperations`.

## Reporting To Confluence

Generate local report:

```bash
npm run confluence:report -- --dry-run
```

Push to Confluence:

```bash
npm run confluence:report -- --update-confluence
```

The script reads `confluence-config.json`, which is gitignored and must not be committed.

The report uses static coverage:

- TC ID in `test(...)` or `data/scenarios/**/*.ts` = active;
- TC ID in `tests/api/**/*.spec.ts` = active when it appears in a `test(...)` title;
- TC ID in `data/api-scenarios/**/*.ts` = active when scenario data explicitly maps to a TC ID;
- TC ID in `test.skip(...)` = skipped;
- TC ID in the source implementation-aware spec only = pending.

It does not currently show latest runtime pass/fail history. To add that, wire in Playwright JSON reporter output.

## Active / Skipped / Pending Meaning

For the generated Confluence report:

| Status | How it is detected |
| --- | --- |
| Active | TC ID appears in a `test(...)` title, `data/scenarios/**/*.ts` `tcIds`, or `data/api-scenarios/**/*.ts`. |
| Skipped | TC ID appears in `test.skip(...)`. |
| Pending | TC ID exists in the source implementation-aware spec but is not found in active or skipped automation. |

For Playwright runtime results, use the HTML report from the latest execution. Runtime pass/fail and static coverage are intentionally separate signals.
